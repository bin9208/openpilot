# 프로젝트 개발 절차

2026-09-29 사용자 지시에 따라 앞으로 모든 개발에 적용한다.

## 이슈와 브랜치

1. 목표를 검증 가능한 이슈로 나누고 각 이슈에 범위, 완료 조건, 검사 방법을 적는다.
2. 작업 시작 시 AGENTS.md, 이 문서, 해당 이슈와 PR, 최신 검사 결과를 읽는다.
3. 릴리스(main 역할) → 통합(dev 역할) → 작업(feat/fix 역할) 관계를 사용한다.
   실제 브랜치 이름은 원격 상태와 배포 경로를 확인하여 정한다. 이름을 반드시 main/dev로
   바꿀 필요는 없으며 Actions 실행을 위해 기본 브랜치를 교체하지 않는다.
4. 이슈별 작업 브랜치에서 수정한다. 기본 이름은 codex/feat-<이슈>-<설명> 또는
   codex/fix-<이슈>-<설명>이다. 기존 미커밋 작업은 보존하고 섞어 커밋하지 않는다.
5. 별개의 새 문제는 새 이슈로 분리한다. 기존 완료 조건 미달이나 회귀는 원래 이슈를
   다시 열고 재현 조건을 추가한다.

## 검사 단계

| 시점 | 목적과 검사 | 소요시간 목표 |
| --- | --- | --- |
| 작업 브랜치 push마다 | diff 검사, 문법·정적 검사, 변경 영역의 빠른 단위 테스트 | 약 5분 이내 |
| 통합/릴리스 대상 PR 생성·업데이트·재개 | 실제 빌드, 통합·회귀 검사, 문서 정책 검사; 가능한 경우 병합 결과 기준 검사 | 약 15분 |
| 통합/릴리스 브랜치 push | 병합된 커밋의 빌드·통합 상태를 별도 확인 | 약 15분 |
| 릴리스 | 검증된 커밋으로 패키지 생성 및 산출물 확인 | 필요한 시간 |
| 실기 검증 | 해당 기기·차량·사용 조건에서 사용자가 완료 조건 확인 | 별도 기록 |

시간은 설계 목표이며 정확성 검사를 생략하거나 강제 성공시키는 제한이 아니다.
GitHub Actions의 push 검사는 로컬 커밋 자체가 아니라 원격 push로 실행된다.
필요한 로컬 재현·검사는 병행한다. PR 검사와 push 검사는 별도 이벤트로 설계한다.
필수 검사에서 경로 필터 때문에 검사가 영원히 대기하거나 잘못 생략되지 않도록 한다.

## 병합과 완료

- 최신 PR 변경분에 필요한 검사들이 성공하고 리뷰 지적이 해결된 뒤 병합한다.
- 필수 검사가 누락·실패·취소·부적절하게 생략되면 병합하지 않는다. 새 커밋 뒤에는
  이전 커밋의 성공을 대신 사용하지 않는다. 기준 브랜치 변경 시 통합 검증의 유효성을 확인한다.
- 통합/릴리스 브랜치에는 가능한 보호 규칙으로 PR 및 필수 검사를 강제한다.
  저장소 요금제·권한상 불가능한 경우 그 한계를 기록하고 동일한 수동 병합 절차를 지킨다.
- Actions 성공은 실행한 검사 범위에 대한 증거다. 정적 검사 성공을 빌드 성공으로,
  Linux 빌드 성공을 대상 기기 또는 실차 정상 동작으로 표현하지 않는다.
- CI 검증 완료, 병합 완료, 사용자 실기 검증 완료를 구분한다. 실기 검증이 완료 조건이면
  해당 결과가 나올 때까지 이슈를 완료 처리하지 않는다.
- 사용자에게 진행 상황, 실패 원인, 남은 검증을 전달하여 사용자가 진행 속도를 조정할 수 있게 한다.

## 기록과 기존 문서 정책

GitHub 이슈와 PR을 진행 상태의 기준으로 삼는다. 로컬 Markdown에는 이슈/PR 링크,
목표와 상태, 변경 커밋 SHA, 실행 명령과 결과, Actions 실행 링크, 완료 시 발생한 문제,
미해결 사항과 실기 검증 결과를 기록한다. 기록을 남겼다는 사실만으로 완료를 주장하지 않는다.
사용자 동작 변경 시 기존 AGENTS.md의 한/영 사용자 문서 및 집중 테스트 갱신 정책도 적용한다.

## CI 기반시설 전환 항목

정책 채택과 실제 원격 강제 적용은 구분한다. CI 전환도 별도 GitHub 이슈와 PR로 진행한다.
2026-09-29 로컬 파일 점검에서는 다음 차이가 확인되었다. 원격 설정과 실행 상태는 미확인이다.

- .github/workflows/tests.yaml: carrot-wip push에만 빌드 연결, pull_request 비활성.
- .github/workflows/user-docs.yaml: PR 검사 활성, push는 carrot-wip만 대상.
- 작업 브랜치의 빠른 검사, PR 빌드 검사, 통합 후 검사 분리가 필요하다.
- 실제 통합/릴리스 브랜치 매핑, 보호 규칙 및 필수 검사 이름을 확인해야 한다.
- 변경한 워크플로를 실제 작업 브랜치 push와 PR에서 실행하고 SHA와 결과 링크로 검증해야 한다.

Self-hosted runner와 외부 정적 리뷰 도구는 필요성·운영비·권한을 확인한 후 별도 이슈로 도입한다.
Self-hosted runner는 신뢰하지 않는 PR 코드에 비밀정보나 내부망을 노출하지 않도록 격리한다.
조직 생성, 유료 요금제 전환, 유료 서비스 연결은 이 정책만으로 자동 수행하지 않는다.

## 적용 브랜치 (이슈 #41)

- `main`: 릴리스 승격 대상. 최초 기준 `43203371004e035bdb70a00a8dad29a4b657c6c3`.
- `dev`: 기본 브랜치이자 통합 대상. 최초 기준 `e905f0dc54c29e427de2b0d5819dc5d45e8da639`.
- 새 이슈: 최신 `origin/dev`에서 `codex/feat-<번호>-<설명>` 또는 `codex/fix-<번호>-<설명>` 생성.
- 작업 PR은 `dev`, 릴리스 PR은 `dev`에서 `main`으로 보낸다.
- `carrot-wip`은 기존 upstream 미러로 유지한다. 이전 네이버 브랜치와 기존 설치 경로는 보존한다.
- 기존 Wiki/NAS 발행의 `carrot-wip` 대상은 이번 변경으로 이동하지 않는다.
- `main`의 최초 커밋은 기존 기준점이며 새 실차 검증을 완료했다는 뜻이 아니다.
- 필수 검사: `fast checks`, `integration gate`, `check mapped user docs`.
- `integration gate`는 실제 빌드/기존 회귀 검사, 네이버 통합 검사, APK 소스/패키징 검사가
  모두 성공해야 통과한다. 필터 없이 PR 및 병합 후 push에서 실행한다.
- 빠른 검사의 실행 목표는 약 5분(타임아웃 7분)이며, 통합 검사는 빌드를 생략하지 않는다.
- main은 최초 dev 승격 PR에 포함된 CI로 검증한다. main에 정책 파일이 들어가기 전에도
  서버 보호 규칙은 필수 검사가 없는 PR의 병합을 차단한다.
